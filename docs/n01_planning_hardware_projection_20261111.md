# N-01 规划耗时上界估算（CPU/GPU 用满时）

> 结论：**规划核心的下限约 8–14 ms**（2 m ≈ 7–9 ms，4 m ≈ 8–10 ms，6 m ≈ 9–14 ms）。
> 但这要求 **路径重采样 + 去掉重复全局规划 + 关键线程独立**；
> 只把现有代码铺到 8 核上，6 m 目标仍要 **150–250 ms**；
> 只把线程挪到隔离核、代码不动，仍要 **~2 s**。
> GPU（本机只有 UHD 630 集显，无 CUDA）对规划核心没有额外收益，它的价值在建图/点云。

## 1. 基准：隔离核上直接跑 `minSnapTraj`

独立小程序链接 `libtraj_utils.a`，`taskset -c 7`（isolated + idle），同一份 `polynomial_traj.cpp`：

| 路径点数 n | 矩阵 6(n−1) | min-snap（中位） |
|---:|---:|---:|
| 7 | 36 | 0.34 ms |
| 13 | 72 | 1.82 ms |
| 20 | 114 | 6.43 ms |
| 27 | 156 | 13.69 ms |
| 33 | 192 | 25.79 ms |
| 39 | 228 | 41.10 ms |
| 80 | 474 | 311.25 ms |
| 119 | 708 | **977 ms** |
| 160 | 954 | 2306 ms |

对比同一时刻在 cpu0（其他核 90% 忙）跑：119 点 1213 ms —— 争抢只占约 20%，
**算法本身才是 80%**。这也和现场日志（39→36.5、80→291、119→978 ms）对得上。

## 2. 为什么"给 8 核"不会自动变快

`minSnapTraj` 里 `Eigen::MatrixXd::inverse()` 走的是 `PartialPivLU`，**Eigen 3.4 的 LU 是单线程**；
而且代码对同一个 A 调了 **5 次** `A.inverse()`（`polynomial_traj.cpp:128/157/158/159`），
对同一个 `Rpp` 调了 **3 次** `Rpp.inverse()`（:149–151）。
所以：

- 只加 `taskset`/多线程编译：**0× 提升**；
- 缓存 A⁻¹、复用 Rpp⁻¹：约 **3–3.5×**；
- 换 OpenBLAS/MKL 的并行 LU（本机目前只有单线程 reference LAPACK）：再加 **2–3×**；
- 利用 A 的 6×6 块对角 + Rpp 的带状结构：**10–100×**，直接把 708×708 稠密求逆变成 119 个 6×6 小求逆 + 带状解。

## 3. 三种"用满硬件"的估算

预算项：A\* 4 ms（p50 3.5，已接近下限）、局部 B 样条 2–4 ms（p90 3.9）、
go→A\* 派发 1–2 ms（关键线程独立后）、发布 1–2 ms。

| 方案 | 2 m（39 点） | 4 m（80 点） | 6 m（119 点） |
|---|---:|---:|---:|
| 现状（单线程 + 重复全局规划 + 争抢） | 206 ms | 2364 ms | 2483 ms |
| 仅挪到隔离核，代码不动（仍重复规划） | ~90 ms | ~640 ms | ~2.0 s |
| 8 核并行 BLAS + 复用 A⁻¹ + 去掉重复规划 | ~14–18 ms | ~53–78 ms | **~160–260 ms** |
| **A\* 路径重采样 0.3 m + 块/带状求解 + 去重 + 线程解耦** | **~7–9 ms** | **~8–10 ms** | **~9–14 ms** |
| 再加 GPU 接管建图/点云 | 同左 | 同左 | 同左（规划不再变快） |

重采样后点数：2 m→7 点、4 m→13 点、6 m→20 点；即使**不**换块求解、只用现在的稠密 inverse，
6 m 也只要 6.4 ms（表 1），所以这一步是性价比最高的。

## 4. GPU 能帮什么、不能帮什么

- 本机是 **Intel UHD 630 集显**（i915 在用），没有 CUDA；FP64 很弱、共享内存带宽，跑 708×708 LU
  的传输+启动开销会吃掉收益，**不适合**做 min-snap。
- GPU 真正适合的是 **建图 raycast**（现在 80 ms/帧、5.8 Hz，单线程占用 ~0.5 核）、
  点云预处理和可视化；把它挪走后，规划线程不再被 80 ms 回调堵住，派发抖动从 4–357 ms 降到 ~1–2 ms。
- A\* 只有 3–7 ms（340k 格 2D 栅格），上 GPU 的 kernel/传输开销不划算，不如把全局栅格降到 0.1 m 或加 JPS。

## 5. 端到端还要注意

如果你说的"规划完成"是 `/n01/live_navigation/hive2_candidate_path`（给跟踪器用的候选路径），
`trajectory_monitor` 还有一个 0.25 s 的定时重发；规划核心再快，端到端也会被这个周期卡在 ~0.25 s。
把它改成"收到新 B 样条立即算/发"，端到端才能到 **~15–20 ms**。
