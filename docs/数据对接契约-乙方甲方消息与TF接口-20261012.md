# 乙方×甲方 数据对接契约 —— 从代码层面梳理（2026-10-12）

> 本文件只依据**源码/配置/launch 的静态事实**整理（未运行任何命令），
> 回答"乙方导航栈与甲方 HiveCore 系统之间到底有哪些数据接口、谁发谁收、
> 消息是什么、frame 怎么对齐"。运行时实测（TF 树 dump、话题 hz）见
> 《导航集成现状诊断-甲方乙方边界与断点-20261012.md》。

## 0. 一句话结论

乙方导航栈整体"夹"在甲方两条数据带上：
- **上游感知/定位**：甲方 Livox 预处理器 `lidar_cloud_preprocess_node` 发点云
  `/livox/lidar/geo_filtered`；甲方 SLAM `slam3d_node` 发定位位姿 `/robot_pose`、
  定位状态 `/localization_status` 与地图系 **map**。
- **下游底盘**：乙方经 `gate_node` 门控后把 `/cmd_vel` 交给甲方 `steer_drive_node`
  监督器，再由 CM 端 `chassis_controller` 执行；底盘 `chassis.odom.publish_tf=false`
  **故意不发 odom→base_link TF**，odom 帧在真实 TF 树上不存在。

代码级接口共 **16 个节点**（乙方 8 + 甲方 8）、约 **28 条消息接口**、**1 条
TF 补桥**（乙方 `pose_tf_bridge` 补 map→base_footprint）。全部对接点都在
`dynacbf_real.launch.py` 里显式声明，见 §3。

## 2. 数据流总图（代码真实 remap）

```
甲方                    乙方                                        甲方
┌────────────────┐   ┌─────────────────────────────────────────┐   ┌────────────────┐
│ livox driver   │   │ local_map   ─→ gridmap/local_pcd/for_obs │   │ steer_drive    │
│ /livox/lidar   │   │   └─ obs_kf → /obs_predict_pub           │   │ 收 /cmd_vel    │
│   ↓ preproc    │   │ planner: cloud←local_pcd                 │   │   ↓            │
│ /livox/lidar/  │   │   sensor_pose←/robot_pose               │   │ chassis_ctrl   │
│  geo_filtered ─┼──→│   body_pose←/robot_pose                 │   │ 执行→/odom    │
│                │   │   └→ planning/bspline ─┐                │   │   (无TF)       │
│ slam3d_node    │   │ bspline_path_sampler ←─┘                │   │                │
│  /robot_pose ──┼──→│   → global_path                          │   │                │
│  /localization ┼──→│ local_planner ← curr_state+global+obs   │   │                │
│  /localization_│   │   → local_plan/cmd_move                  │   │                │
│  _status       │   │ controller → /curr_state, /cmd_vel_nav  │   │                │
│                │   │ gate_node 门控 → /cmd_vel ──────────────┼──→│                │
│                │   │ pose_tf_bridge: /robot_pose→map→base_ft ┤   │                │
└────────────────┘   └─────────────────────────────────────────┘   └────────────────┘
```

三条跨界链路：
1. **感知**：`/livox/lidar/geo_filtered` → local_map →（乙方内部）→ planner `cloud`
2. **定位**：`/robot_pose` + `/localization_status` → controller / planner / gate / bspline / bridge
3. **控制**：controller `/cmd_vel_nav` → gate → `/cmd_vel` → 甲方 steer_drive

## 4. TF 树对接（frame 契约）

### 4.1 甲方声明的 frame（slam3d_common.yaml:16-20）

```
map_frame:      "map"           # 甲方全局系
tracking_frame: "base_footprint" # SLAM 输出 TF 的 child（不是 base_link！）
scan_frame:     "lidar_link"    # 点云 frame
imu_frame:      "imu_link"
mola_vehicle_frame: "base_link"
```

### 4.2 甲方本体 TF（robot_state_publisher，URDF root=base_footprint）

```
base_footprint → base_link → …（腿关节）→ lidar_link（SLAM 雷达）
静态边（static_tf_publisher，static_tf_publisher_params.yaml:31-49）：
  lidar_link → imu_link
  imu_link → livox_frame
```

### 4.3 甲方底盘 TF：**不发**

`robot_motion.yaml:91-92` 注释原文：
> Default off: avoid odom→base_link stealing parent from RSP / SLAM TF.
> `chassis.odom.publish_tf: false`

所以 **odom 帧在真实 TF 树上不存在**（LookupException 的根因）。导航的
全局 frame 只能是 `map`（甲方 SLAM），不能用 `/odom` 坐标系做 TF 定位。

> **补充（代码级权威结论，来自 manual_slam3d + LocalizationStatus）**：
> - 甲方产品里**根本没有 odom 帧**这一设计：slam3d_node 直发 `map→base_footprint`
>   （map_frame=map、tracking_frame=base_footprint），不是 `map→odom→base_link`。
>   "odom 帧不存在"是设计如此，不是断链。
> - slam3d_node 是甲方**唯一的 map 系 TF 发布者**（manual_slam3d.md:36：
>   "one TF writer map → tracking_frame (default base_footprint)"）。
> - 该 TF **并非一直发布**：它只在 `enable_processing == true`（即 Mapping 或
>   Localization 内会话非 Stopped）时由这个唯一的 broadcaster 发布
>   （manual_slam3d.md:251-252）。`control_signal_enable_publish_tf` 只是
>   wire-compat 别名（恒等于 enable_processing），不是独立开关。
> - **断链主因**：默认 `localization.map_path=/root/resources_storage/cloud_map_pgo.pcd`
>   （localization_params.yaml:19）在真机上**不存在**（实际文件在
>   `/home/demo/resources_storage/cloud_map_pgo.pcd`）。未 override map_path →
>   loadMap 失败 → 内会话保持 Stopped → `enable_processing=false` → 不发布
>   pose/TF。README.md:45 也明示 "always override map_path:=…"。
> - 运行时 TF dump 里 `map` 只连 `sliding_map`，那条边是**乙方 GridMap 自己广播的**
>   （grid_map.cpp:1109-1123），不是甲方——恰好证明 slam3d_node 没在发 map→base_footprint。

### 4.4 乙方需要的 TF 查询（代码）

| 节点 | 查询 | 代码 | 断链后果 |
|---|---|---|---|
| controller | `map→base_link` | controller.py:95-96 | `/curr_state` 静默不发布，MPC 饿死 |
| local_map | `map→base_link`、`map→lidar_link` | local_map.cpp:179/191 | 点云无法转 map，栅格空 |
| gate（降级） | `map→base_footprint` | gate_node.py:174 | 门控判据失效 |
| planner grid_map | （map 系，经 sensor_pose） | grid_map.cpp | 射线投射无位姿 |

### 4.5 乙方补救：pose_tf_bridge

- 订阅 `/robot_pose`（header=map，child=base_footprint），广播 map→base_footprint 边
- 一旦甲方 map→base_footprint TF 正常，bridge 检测到重复边自动停发
- 甲方修好后把 launch 里 `enable:=false` 即可移除（launch:306-318）

## 5. 关键消息字段（LocalizationStatus，代码只读）

`release_slam_3d/…/hivecore_slam3d/msg/LocalizationStatus.msg`：
- `registration_output_localization_mode`：`MODE_TRACKING=0` / `MODE_RELOCALIZATION=1`
- `registration_output_pose_published`：位姿已发布
- `registration_output_tf_published`：TF 已发布
- `registration_output_fitness_mse`：配准拟合误差（gate 门限 0.5）
- `control_signal_enable_processing`：处理使能
- `control_signal_session_mode`：`"stopped" | "relocalization" | "tracking"`

gate_node 判据（gate_node.py:140-147）：`enable_processing && mode==TRACKING &&
pose_published && tf_published && fitness≤max_fitness`。

## 6. 断点（为什么现在不动）与代码根因

| 断点 | 代码级证据 | 后果 |
|---|---|---|
| 甲方 map→base_footprint TF 未发布（2026-10-12 实测树裂） | slam3d_node 只在 `enable_processing=true`（定位/建图内会话非 Stopped）时发；默认 `map_path` 在真机不存在→loadMap 失败→内会话 Stopped | controller 的 `map→base_link` lookup 抛 ConnectivityException → `/curr_state` 不发 → local_planner 饿死 |
| 甲方底盘不发 odom TF | robot_motion.yaml:92 + 甲方产品无 odom 帧设计 | odom 帧不存在，不能靠 `/odom` 兜底 TF |
| `/cmd_vel` 多发布者 | 3 个节点（gate/preproc/person_follow） | 现场 10Hz `/cmd_vel` 是甲方遥操心跳，非导航 |

补救已在代码内（不是甲方改动）：`pose_tf_bridge` 订阅 `/robot_pose` 补出
map→base_footprint TF 边 → controller `/curr_state` 恢复 → 全链苏醒。

## 9. 甲方已定义但未部署的接口（避免误对接）

`hive2-motion` 的 `interfaces` 包定义了若干 Action，但**运行时都没有 server 节点**：
- `NavigateToGoal` —— 甲方**没有**导航 Action server（导航能力由乙方本栈提供）
- `SlamMode`、`MoveWheel`、`VisionPersonTrack` —— 均无 server（PersonTrack 仅被
  person_follow 作为 client 消费）

结论：**不能期待甲方提供"导航目标"Action**；目标的唯一正常入口是乙方
`move_base_simple/goal`（navi_mode=1）或 `initial_path`（navi_mode=3）。
