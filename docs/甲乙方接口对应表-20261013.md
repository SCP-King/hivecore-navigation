## 二、甲方数据启动依赖表

| 数据 | 需启动哪个甲方 launch/脚本 | GUI 操作 | 前置节点/TF 依赖 | 何时才算真正就绪 | 未发布时乙方处理 |
|---|---|---|---|---|---|
| /odom | start_hive2_motion.sh | 无 | 底盘上电 + motion stack | 持续发布 ~50Hz、position/orientation 有限 | 缺→preflight FAIL，不启动导航 |
| /livox/lidar/geo_filtered | GUI-SLAM启动（gui_slam_console） | 无(默认开) | preprocess enable_forward:true + **有订阅者才发** + TF 链 base_link→lidar_link（static_tf_publisher_node） | 实际订阅后 ~10Hz、frame=lidar_link | **乙方默认输入**；无数据→preflight FAIL，不静默回退 raw |
| /livox/lidar（显式可选） | start_hive2_motion.sh | 无 | Livox 上电 | 持续 ~10Hz 有效点云 | 仅显式切回并确认 frame TF 可解析；不静默回退 |
| base_link→lidar_link TF | GUI-SLAM static_tf_publisher_node(/tf_static) | 无 | GUI-SLAM | tf2 可解析 base_link→lidar_link，平移≈(0.295,0,0) | 缺→local_map 卡 wait for lidar，preflight FAIL |
| base_footprint→base_link TF | 运动栈 RSP | 无 | 运动栈 | 唯一 z 定义（现为双定义冲突） | 冲突→preflight FAIL 提示甲方修 |

## 三、三种"Topic 存在"状态的判别（不只看名字）

| 状态 | 判别法 | 现场实例 |
|---|---|---|
| ① 节点没启动，Topic 不存在 | `ros2 topic list` 无该名 | 未启 GUI-SLAM 时 /livox/lidar/geo_filtered 不存在 |
| ② Topic 存在但无实际数据 | 有名字 + `ros2 topic info` 有发布者，但**真实订阅 3.5s 取不到帧** | /robot_pose（Idle 下无 pose 数据） |
| ③ Topic 有数据但类型/QoS/TF/时间戳不符 | 订阅到帧，但 frame 名 / QoS 不匹配 / 时间戳漂移 / TF 断链 | 原始点云 frame=livox_frame 但乙方 buffer 缺 livox_frame TF → 无法转出 |

> **乙方 preflight_hivecore.sh 全部按「真实订阅」实现**（第 2 节），不把 topic list 存在当就绪。

## 四、M1 正确启动顺序（乙方视角，实测验证）

1. **甲方运动栈**：`start_hive2_motion.sh`（/odom + /livox/lidar + base_link→lidar_link）。已运行则跳过。
2. **甲方 GUI-SLAM**：`source setup_runtime.sh && ros2 launch hivecore_console_slam3d gui_slam_console.launch.py use_sim_time:=false`
   （= 桌面「GUI-SLAM启动」。提供 base_link→lidar_link / base_link→livox_frame 静态 TF + /livox/lidar/geo_filtered）。已运行则跳过。
3. **乙方自检**：`bash scripts/start_hivecore_deps.sh`（只检查/提示）→ `bash scripts/preflight_hivecore.sh`（真实订阅全项）。**全部 PASS 才继续；FAIL 停止。**
4. **乙方干跑**：`bash scripts/run_m1_safe.sh`（= preflight + gate_cmd_out:=/cmd_vel_dryrun）。
   **不驱动底盘**。确认 MPC/规划/门控都出解后，才考虑真机。
5. **（未来，双 RSP 甲方修复后）真机**：`bash scripts/run_m1_safe.sh --real-cmd`（需 YES 二次确认）。

> 当前现场：第 3 步 preflight **FAIL（双 RSP）** → 暂停在 3，不进入 4。符合用户边界「依赖检查未通过前不进入真机导航控制」。

## 五、2026-10-14 M1 默认输入切换 + local_map 实读入证据

### 5.1 默认值的统一（方案 A）

经审计与现场矛盾确认，乙方仓库默认点云输入由 `/livox/lidar`（frame=livox_frame，需额外
`base_link→livox_frame` TF，现场易断）统一翻转为甲方 SLAM preprocessor 的
`/livox/lidar/geo_filtered`（frame=lidar_link，`base_link→lidar_link` 静态边出自
GUI-SLAM `static_tf_publisher_node`）。改动文件：

| 位置 | 改动 |
|---|---|
| `src/dynacbf_bringup/config/dynacbf_real.yaml` | `lidar_topic: "/livox/lidar/geo_filtered"`（注释含实证） |
| `src/dynacbf_bringup/launch/dynacbf_real.launch.py` | DeclareLaunchArgument 默认 `geo_filtered`，文案注明显式回退条件 |
| `src/dynacbf_perception/config/config.yaml` | 同上 |
| `src/dynacbf_perception/src/local_map.cpp:85` | C++ `declare_parameter` 默认 `geo_filtered` |
| `scripts/run_m1_safe.sh` / `run_dryrun.sh` / `run_m1_odom.sh` / `m1_preflight_and_run.sh` | launch 参数 `lidar_topic:=/livox/lidar/geo_filtered` |
| `scripts/preflight_hivecore.sh` | MODE 默认 `LIDAR_TOPIC` → `geo_filtered`；2b 主检查、5b TF 按实测 frame、5c 双 RSP 计数修正、2c WARN 守卫 |

**规则**：原始 `/livox/lidar` 仍作为显式可选配置保留，但只有在其 frame=livox_frame 的 TF
（`base_link→livox_frame`）被 preflight 5b 确认可解析时才允许使用；**无静默自动回退**。

### 5.2 local_map 实读入验证（2026-10-14）

以 M1 参数独立启动乙方 `local_map`（`-p lidar_topic:=/livox/lidar/geo_filtered`），只读订阅甲方数据，
观察到乙方确实在消费（进程日志与输出话题双证）：

- `/local_pcd`：frame=`odom`，width **2455** 点，point_step 16字节，~5Hz；
- `/gridmap`、`/for_obs_track`、`/ellipse_vis`：~5Hz 持续；
- `updateTF()` 组装成功（`base_link→lidar_link` 静态边，平移约 (0.295,0,0)）。

这证明**默认 geo_filtered 条件下乙方链路可读**；此前提下的读入成功不得与「完整导航
Dry-run / M1 正式验收通过」混淆——双 RSP 冲突仍是独立阻塞项。
