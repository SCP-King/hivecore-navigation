# G4.12：历史建图 0.30m 与 Hive2 运动模型 0.90m 的 map 高度冲突核对（2026-10-30）

**最重要的改判**：不能再把 Hive2 0.90m 固定 URDF 链当作这份**历史 PCD 建图时实际采用的默认链**。它仍然是将来四轮移动机体的权威描述，但 **历史地图按 0.30m 机体偏移形成**的假说，已由用户上报的 TF 时间轴、三帧 raw 点云转换和 PCD 表面统计强烈支持。此文件只是基于用户传来的时序审计和已核对的项目源码，未在本轮独立重新加载原始大型 Bag 与 PCD。

## 1. 三组用户上报观测

| `/tf_static` `base_footprint→base_link` | +0.90m，1 条，stamp 1793112591.7 | 运动栈曾发布静态 TF；**一次发布并不代表它只瞬间生效** |

**新的地面候选区间（原地图 map 中，局部）**：约 **-0.60 ～ -0.50m**；不能设成 -0.90，也不该继续默认 0。雷达物理参考点至低簇约 0.9m 的推断与“map 地面不是 0”并不矛盾。真正地面仍需几何/接地或现场测量校准，不能因三组数值咬合就设 `N01_G4_FLOOR_Z_VERIFIED=1`。

## 2. 已从仓库源码找到的直接后果

原来 `n01_offline_integration/historical_tf.py` 的 `SELECTED_MOUNT_HEIGHT_M=0.90`，而 `historical_bag_node.py` 会跳过录制的两条冲突边，**人为重建一个 +0.90m 的 /body_pose、/sensor_pose 和 /cloud**。因此此前真实 Bag 928 帧读取、571 帧 map TF 转换、G3.4 104 次数值限幅通过，证明**软件功能与约束**，但不代表那批重建点云与原历史 PCD 在 Z 上一致。不能用以前 G3 的通过结果反证地图高度正确。

为了不破坏历史 G3 对比：当前**保留** +0.90m 为旧 Bag 功能回放默认值，不擅自改旧数据的含义。新增：
- `historical_tf.mapped_mounts(pose,mount_height_m=.30)`：只读显式换算原 SLAM 动态偏移的候选坐标，不将两个同名边同时放进 TF 图。
- `n01_g4_bag_start_preflight.py` 输出按 channel 分组的 **`tf_mount_edge_evidence_by_topic`**（出现次数、每类原始时间戳首尾）及使用 +0.30 / +0.90 重建的两组 body/lidar XYZ、原始 `map→base_footprint` 四元数。
- `g412_historical_mount_alignment.py`：形成 **`g412_historical_mount_alignment.json`**，诊断同一历史 map 姿态下的 +0.60m 雷达错位；求解**保持原 lidar-map 坐标一致所需的理论 BF 坐标校正**。源码与测试均不发布任何 TF、轨迹或控制指令。

### 数学关系（不仅是 Z 相减）

设原本地图使用 `T_map_bf` 和 `T_bf_bl_old=Trans(0,0,+0.30)`。若改为 Hive2 的 `T_bf_bl_new=Trans(0,0,+0.90)`，又要求雷达在**同一张地图中的实际位置不变**，则在完全相同姿态下：

```text
T_map_bf_new = T_map_bf_old * Trans(0,0,-0.60)
T_map_lidar = T_map_bf_old * Trans(0,0,+0.30) * T_bl_lidar
            = T_map_bf_new * Trans(0,0,+0.90) * T_bl_lidar
```

如果 `T_map_bf_old` 存在 roll/pitch，-0.60m 必须由其四元数旋转到 map 坐标后加到原始平移里，不能只修改 world Z。**这仅是相同 LiDAR 坐标下的 SE(3) 等价推导，不是允许实时更改 SLAM 发布的 `map→base_footprint` 的操作指令**。具体上线要由 SLAM/底盘双方决定地图坐标迁移、重定位策略和唯一 TF 权威。

数值例（首帧接近水平）：原 Bag `map→base_footprint.z≈+0.00349`，原 SLAM +0.30 ⇒ LiDAR 约 map +0.3035；若未调整直接换 Hive2 +0.90 ⇒ LiDAR 约 map +0.9035，相差 0.60；若仍用原地图但以 +0.90 为机体权威，理论上 map→BF.z 应接近 -0.5965 才能恢复同一个 map LiDAR z≈+0.3035。**-0.5965 是坐标一致性计算，不是已测底盘实际位置。**

## 3. 现在该怎样快速让整个导航框架贯通

**离线功能路径**：在机器人/控制器隔离的开发域内，以**历史建图 +0.30m** 的回放坐标约定复现 PCD、点云、历史定位，并把局部地面约 -0.55m 作为**明确标注的研究假设**，使 SCAN/G4 mode3 的路径 Z 和 `/body_pose` 一致（SCAN `pathCallback` 会给参考 Z 加 `grid_map.body_height`，需分别与目标坐标对齐；不能简单照抄上游 0.4m 或把 Hive2 0.9m 直接当作所有碰撞参数）。该阶段的 G4→SCAN→G2→G3 可以先测试**话题流贯通与研究可视化**，而不应宣称安全通行。

**实机定位路径（后续）**：应使用 Hive2 真实 +0.90m 机体 URDF，确保 SLAM 旧 +0.30m RSP **完全关闭**，之后显式核对 SLAM 地图/定位坐标怎样对齐已有 PCD；不能保留旧 `map→base_footprint` 数值不变就强行换成新机体链。只读核对原位 LiDAR/点云在旧 PCD 下的几何重合，然后再计划安全可控的移动。若现有地图与新链不兼容，需做校准或地图重定位，而不是任意移动一条 TF 消除 0.6m 的可视化误差。

### 4. 当下不该做的事

- 不要把一次 `/tf_static` 发布误解为“仅在开头闪了一下”；
- 不要依据动态 TF 的频率**独自**证明历史 SLAM 每次查询必定采纳 0.30m；
- 不要把历史 map `Z≈-0.55` 当作实际现场全部地面真值；
- 不要在旧 PCD 下用不补偿的 +0.90m TF 直接生成“可开动”的路径；
- 不要为了跑通 `run_n01_g4_full_chain.sh` 人为写 `N01_G4_FLOOR_Z_VERIFIED=1`，除非已经有现场或地面支撑依据；
- 不要改动甲方运动控制器配置、启动实机、发布 `/cmd_vel` 或声称四轮转向已经完成执行验证。

**本轮提交属于：更新坐标契约、代码可解释性和离线诊断；不包括已实际执行完整 G4→SCAN→G2→G3 新路线。**
