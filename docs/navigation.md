# 导航算法与位姿连续性

状态说明（2026-11-17）：本文件描述已有实现及已知缺口；最新目标方案见[架构第3节](architecture.md#3-目标主链)，尚未全部实现。不得把以下历史接入说明当成当前现场验证通过。

## 当前生产链路

`甲方SLAM／FAST-LIO2 → 状态与点云适配 → A*全局参考 → SCAN局部B-spline → R2审核与场景证书 → C++闭环控制器 → 桌面底盘`。

SCAN是唯一局部几何规划器。`trajectory_monitor.py`只采样、做原生四轮审核并打包当前模型/场景，不再运行SE2搜索或单独生成转向路线。控制器直接消费 `/n01/navigation/trajectory` 的 `NavigationTrajectory`，不通过Path与JSON配对获取执行权限。

`/planning/global_path` 是全局参考；`/n01/navigation/path` 是显示用局部轨迹。控制器运行时由它发布实际保持/执行的前段；控制器未运行时，`trajectory_display.py`显示SCAN提案。显示节点看到控制进度心跳后让出显示，不拼接未审核全局后缀。Path和诊断JSON不参与底盘输出授权。

## 静态参考与实时障碍：现状与待修正项

当前标准配置仍启用`grid_map.static_prior_as_cost=true`：局部窗口内背景地图点作为全局A*的倍率12软代价，窗口外作为硬障碍；当前扫描的有效障碍点补入全局硬占用。这并非完整局部融合占用覆盖全局。全局还会按碰撞高度及地面截止过滤点，因此GUI看见的累积表面不必然进入全局障碍。该设计存在“可见旧障碍可被穿越、当前扫描未命中就缺少硬占用”的问题，不能当作预期行为。

GridMap已保存三维射线和世界变化证据；确认清除需要独立扫描证据，同帧命中优先，新命中撤销清除。当前源码中，覆盖可过期，而部分过期占用仍保留碰撞风险，存在残留长期阻挡的缺口。不能再将“1.5秒后恢复原先验”作为统一现状；也不能把过期障碍无限保留当作已经解决历史更新。

全局A*折线缩减后生成min-snap曲线，最终曲线按同一融合环境逐段采样复核，穿越占用或超采样预算时回退A*折线（`planner_manager.cpp` `reference_valid`），不回退即报`global_reference_collision`。场景确认阻断（`takeRouteMapChange`且路线前方出现硬占用）立即触发全局重规划，不再等待连续失败次数。

**盲区与未观测的规划语义（2026-11-17五次修订）**：导航不推断盲区。只有明确障碍（静态地图点、实测命中、动态预测点）不可通行；未扫描、被遮挡、地图外、稀疏缺失一律不进入代价、不减速、不停车。规划侧由`grid_map.unknown_as_obstacle: false`实现（回滚设`true`）；执行侧已关闭`trajectory_monitor.require_observed_space`（2026-11-17），取消覆盖门控与前缀限速，只保留数据断流、实测碰撞与求解失败检查。盲区、玻璃、负障碍由甲方建图与传感器布置负责，按OPEN-07书面确认。证据：`n01_runtime/reports/fusion_recheck9_20261117/`，规划侧3/4目标产出SCAN轨迹，未做运动验证。

不设探索式改道：不再按覆盖边界选择前沿，局部目标始终沿全局参考选取。前沿搜索代码已于2026-11-17删除，生产链不再包含该路径。

目标规则：远处按有效累积地图／离线PCD避障；近处按实际命中和真实射线更新；确认清除跨窗口保存，历史未确认降质而非永久硬叠加，遮挡不冒充空闲。全局、SCAN和执行复用融合结果；已知路线不穿障；未观测区域不单独标识、不触发改道。详见[融合、残留处理与约束披露](architecture.md#31-全局与局部的融合规则)。原始PCD不直接改写，有效规划视图记录更新覆盖。

3秒观测TTL与0.6秒场景时效仅用于诊断，不作为通行许可；模糊回波仍按证据质量处理，不因不确定整体封路。地图和地面定义见[坐标模型](coordinates_and_chassis.md)。

## 延迟定位：测量预测和真实纠偏

实现文件：`delayed_pose.py`、`twist_odometry.py`、`live_scan_bridge.py`。预测参数及观测门限持久化在 `config/live_scan.yaml`、定位和导航launch默认值中。

1. 保留原始SLAM位姿及源时间戳，不用当前时间冒充新测量。
2. 原始 `/odom` 的位置增量历史上约为其速度积分的两倍。导航内部改用**测量到的机体线速度**，按原始时间间隔及odom姿态旋转到里程计坐标，以梯形积分重建平移；姿态沿用测量odom姿态。只改变导航内部缓存，不修改原始odom、轮径、底盘参数或桌面进程。
3. 延迟真实定位到达后，插值取得其原始时间戳对应的局部里程计，将该定位传播到当前测量时刻；与此前预测比较后，平滑更新修正历史。这里的历史插值用于时间配对，向当前的推算依赖实测运动，不是凭最后速度无限外推。
4. 当前 `/body_pose` 和扫描时刻 `/scan_body_pose`、点云采用同一因果修正历史。扫描时间戳不改；不拿最新TF替代扫描时刻TF。旋转原始雷达云使用时间匹配的预测机身位姿与机身至传感器外参，避免继续依赖迟到的map→body TF。
5. 新定位造成的修正从此前预测连续开始；默认最短0.8s，修正平移速率≤0.04m/s、角速率≤0.08rad/s。参数是修正项的速度，不是车辆速度限额。绕有效机身参考点插值，避免远处odom原点放大旋转误差。

| 约束 | 默认值及行为 |
|---|---|
| 原始定位预测时限 | 5.0s，源时间戳和接收年龄均受限；重复/乱序定位不延长有效期 |
| 锚点后位移/转角 | ≤0.12m / 0.20rad，独立于时限；高速下会更早耗尽预算 |
| 里程计接收/时间戳年龄 | ≤0.2s / 0.4s；时间配对最大间隔0.08s |
| 里程计断档/姿态跳变 | 开启新积分段，等待断档后真实定位锚点，不跨未知运动外推 |
| 定位纠偏跳变 | 超过0.15m或0.17rad锁定故障，需要重置定位链路；不缓慢掩盖重定位跳变 |
| 定位状态/激光 | tracking、reloc_ok与新鲜点云继续独立检查，预测不能替代障碍观测 |
| 不确定性 | 输出位姿协方差随锚点年龄及创新量增加；诊断标记ODOMETRY_PREDICTED并保留原始年龄 |

因此5s不是允许任意速度盲走5s。低速短时定位迟滞在测量反馈、位移和转角预算内衔接；位移仍限0.12m、转角仍限0.20rad，超预算仍停车。速度反馈/航向的物理精度尚需实机核验，合成测试不替代标定。甲方LO的250ms参考轨迹等待逻辑未被修改，预测是下游连续性补偿。

路线使用有效预测控制位姿维持连续跟踪，同时保留原始定位供记录与诊断。恢复前要求链路有效稳定时间≥1.2s且≥4次控制位姿更新；不足0.3s的暂时不可用不清空累计稳定时间，但不可用时间不计入稳定时长；新预测桥未启用时沿用原始定位检查。失效时禁用执行器，2s内确认停驶，再等最多30s恢复稳定，重新检查/规划同站；超时保留站点暂停。手动接管、急停或用户取消不自动恢复。

## MOLA扫描释放与同步等待

甲方主机等待当前 `scan_ref` 最多250ms，而MOLA默认允许扫描等IMU覆盖500ms。扫描在主机超时之后才释放时，LO后台仍计算，但该扫描结果无法被本次同步调用采纳，主机继续发布数值不变、时间戳前进的保留位姿。图上tracking在线不代表位置真正更新。

建图与定位launch通过 `mola_pipeline.py` 将供应商原始pipeline与项目 `config/mola_localization_overrides.yaml` 合成到运行目录，不修改供应商安装，也不复制一整份配置进入源码。覆盖IMU等待为50ms、待释放扫描最多2帧，给250ms主机预算留出配准时间。IMU覆盖正常时继续融合；迟到时由MOLA降级当前扫描，后续数据正常便恢复。两种甲方模式共用此等待覆盖。该修复没有修改主机硬编码的250ms，极端处理超时仍可能出现。

`held_pose.py`仍拒绝运动中重复的保留位姿，不能靠重新盖时间戳恢复新鲜度。新的真实定位使用原始采集时刻配对里程计并平滑纠偏。恢复门限是停车后的检查，不能将其30s等待时长理解为运动预测许可。

## 有界恢复阶梯（2026-11-17）

局部规划失败不再无限重试：局部绕行用尽 → 全局重规划 → 零速等待并保留目标。次数与等待超时是规划节点参数（`recovery.local_attempts`、`recovery.global_attempts`、`recovery.wait_timeout_s`），**规划节点每次失败时实时读取**，GUI"恢复策略"面板写入即生效。等待阶段只接受三种解除方式：GUI"继续任务"（`/n01/navigation/resume`）、新目标、或超时后自动重试（`recovery.auto_resume`）。状态在`/planning/status`的`recovery_stage`、`recovery_local_attempts`、`recovery_global_attempts`中逐次上报。

## 执行、到达和控制权

统一控制器为 `scan_planner/n01_navigation_controller`，默认未启用，50Hz控制。GUI显式请求后，控制器先反馈自己的start_ready，再接收enable。点选和路线使用同一入口、同一控制器；路线任务归GUI进程而非浏览器页面，页面重连不会取消；各站复用同一控制进程，目标更换重建站点状态，重复轨迹不重置执行进度。

驾驶策略为非负vx、vy=0，机头沿路径；采用切线速度前馈、横向/航向反馈、原生IK/FK复核及实际纠偏命令的制动区间碰撞检查。大航向误差进入同一控制器ALIGN：实测停车、检查当前URDF整段旋转扫掠及全向观测，再旋转；受阻向SCAN请求重规划，SCAN可用当前前向朝向初始化其优化，不另起搜索器。初始控制速度越过真实底盘spin阈值，避免低速加速度斜坡永远被归零。

完整到点轨迹终段根据实际目标距离和方向收敛，不能仅因样条剩余弧长耗尽停车。8cm进入、10cm退出到达区；最终朝向适用于记录路线。测量速度确认停稳至少0.5秒，并等待停车后真实SLAM测量证实位置/朝向，之后才锁存ARRIVED。GUI旧站反馈必须同时匹配task_id与goal_id，不能推进下一站。

控制器直接以publisher GID区分自己的速度和外部实际流量；外部零速也让权，闲置发布者不阻塞启动。手动接管后停止所有自动输出，需显式恢复；急停锁存。保留真实轮角、轮速、舵速、制动距离、场景/控制反馈失效处理；没有第二份聚合就绪灯否决。

## 导航 RViz 环境表面

导航默认显示观测体素的外表面三角网格和地面投影轮廓，隐藏原始点云与膨胀点云。蓝灰为历史/累积地图参考，青绿为当前局部占据表面，金色为统一执行路径；RobotModel 和碰撞包络保留。地面网格沿本次导航拟合平面，不能假定 map 的 z=0 是地面。

显示节点 n01_environment_display 随导航启动，仅发布 Marker/诊断；不修改地图、碰撞、路径或执行器。参考表面最多1Hz，局部表面最多2Hz，默认显示半径12m、地面以上6cm至2.2m。显示体素初始12cm，面数超过24000时自适应放粗，上限30cm；超出预算则报告错误，不悄悄截掉部分地图。表面只包围有回波的体素，不把桌底空隙或没观测到的背面补成实体。轮廓是障碍点的地面投影，不是精准接地外形。

实时层同时检查局部地图消息和桥接扫描时间，超过1s即清除，Marker另有1.5s寿命。历史参考明确用另一种颜色并保留给晚打开的RViz。没有显示订阅者时不重建网格，也不订阅/触发局部占据云导出。可在Displays勾选三个“调试”点云层核对原始观测与规划膨胀；显示模型精细程度不改变导航膨胀或R2模型。

更新后需重启导航以加载显示节点，关闭旧导航RViz后从GUI“导航RViz”重新打开。GUI与launch使用同一配置 src/n01_live_navigation/rviz/n01_live_navigation.rviz；rviz/n01_full_pipeline.rviz 保持相同内容，供手动打开。

## CBF和性能

SCAN负责几何改路。可选CBF是沿名义平移方向的标量速度QP投影，结合实时障碍点和动态轨迹压低速度或停车，不提高名义速度。它不是已标定的全自由度动力学MPC。关闭CBF仍会因定位、路径或底盘约束停车。动态障碍专项实机验收尚未完成。

性能优化包括Release构建、A*同碰撞层可见性重采样、min-snap矩阵求逆复用、原生批量轮组计算、近期有效前缀复核、静态膨胀合并及按需导出可视化。不同地图/模型的基准不能混为实时性能保证，具体样本见 [验证文档](validation.md)。不能未经共享状态同步设计直接把SCAN单线程地图/规划回调改成并发写入。


## 甲方实时建图导航（R2）

总控只选择“方法＝甲方 SLAM3D Lite / 自部署 FAST-LIO2”和“地图模式＝实时 / 离线”。这里离线指已保存PCD，仍使用当前传感器，不是bag回放。

| 地图模式 | 操作流程 |
| --- | --- |
| 离线地图 | ① 启动建图并结束保存PCD（已有地图可跳过）→ ② 启动定位、加载地图并进入跟踪 → 手动启动导航 → 规划后手动启动行驶 |
| 实时地图 | ① 启动实时SLAM（同时建图与估计位姿）→ 等待数据就绪、同步地面 → 手动启动导航 → 规划后手动启动行驶 |

实时模式没有独立定位任务，隐藏PCD加载、重定位和初始位姿控件。导航与行驶不会随着SLAM自动启动；实时SLAM沿用建图录bag、结束保存地图的行为。两个选择运行中锁定，停止后可切换。

以甲方链路为例：选择“甲方 SLAM3D Lite / 实时”，点击“启动实时SLAM”，等待位姿、逐帧点云和底盘里程计就绪。点击“同步地面”，再手动“启动导航”，打开建图/导航 RViz，在已观测区域选择目标并规划，确认路径后再启动行驶。GUI 本身不自动启动SLAM、导航、底盘或雷达。

这个流程不加载旧 PCD，不做旧地图初始位姿匹配，也不需要点击进入 tracking。建图算法仍持续估计机器人在本次 map 坐标系中的位姿；它不是无位姿导航。建图状态只有 session，没有可用的配准质量字段，适配器明确输出 mapping_session_and_fresh_pose，不伪造 map_loaded、reloc_ok 或 fitness。该就绪状态只证明会话活跃和位姿新鲜，不能代表已验证定位精度；扫描配对、里程计预测预算、执行器和手动优先检查继续生效。

| 点云 | 通道与用途 |
| --- | --- |
| 当前逐帧点云 | /livox/lidar/geo_filtered → 导航桥按采集时间配对位姿 → /cloud 与同时间戳 /sensor_pose → SCAN 局部占据/射线清除；用于近期避障 |
| 多帧配准累积点云 | 甲方 /cloud_map → 保留原帧/时间的参考中继 → /grid_map/static_occupancy；全局 A* 参考及 GUI 地面拟合 |

实时参考按甲方地图快照更新，接收端拒绝错误坐标帧、过期/不递增时间戳和超限/损坏消息；SCAN 允许新快照替换参考，离线模式仍只接收第一张静态 PCD。累积图不作为当前扫描进行射线清除。当前实现仍将窗口内参考降为代价，这一缺口按本文件“静态参考与实时障碍”节修正；目标是基于证据融合，而非整窗软化或历史／实测永远取并集。累积点云本身不能保证清除旧物体。

命令行同一入口：先 scripts/runtime/start_localization_stack.sh slam_mode:=mapping；确认地面后，给 scripts/n01_navigation.sh start 设置 N01_NAV_MAP_MODE=realtime、N01_NAV_REALTIME_REFERENCE_TOPIC=/cloud_map、N01_NAV_GROUND_Z/A/B（当前 map 下拟合的平面系数）。这些命令启动感知/规划，不会自动启动车轮。桌面底盘、雷达和 RSP 仍独立管理。

结束建图先停止执行器和导航，再保存 PCD、结束 bag、停止本 GUI 建图进程。建图重启会建立新坐标系，不能直接沿用旧会话路线；目前持久路线仍要求保存 PCD 并进入该地图定位后记录/回放。实时建图导航的实机避障、到点和长时稳定性需现场验收，离线及隔离测试不代表验收完成。

## 自部署FAST-LIO2后端

项目引入并适配FAST-LIO2，支持离线地图定位与实时建图导航，不直接用其私有位姿驱动底盘。外部源码按 `n01_fast_lio2.repos` 和导入脚本固定版本：FAST_LIO `cc3c9e8b1469b33b8072764d6db2348ed6dc597f`，ikd-Tree `e2e3f4e9d3b95a9e66b1ba83dc98d4a05ed8a3c4`。导入/构建与运行入口由 `scripts/n01 fast-lio-*` 管理，源码和第三方依赖保持独立，不把生成结果混入主工程说明。

FAST-LIO2读取原始 `/livox/lidar`、`/livox/imu`，输出隔离在 `/n01/fast_lio/`，私有map/TF经项目适配器转为规范机身帧。甲方后端读取经过预处理的云；两者使用同一机身/地面语义，不能对FAST-LIO2再次应用甲方预处理倾角。上游固定版本是可重现构建信息，不代表原厂版本已完成本站完整路线验收。


## 实时建图输入与启动时序（2026-11-14）

甲方实时建图先等待新鲜点云及稳定IMU窗口，再建立地图坐标系；30秒未满足则退出，不用缺失输入初始化地图。建图注册输入经 `/n01/slam/mapping_scan` 按目标5Hz固定采集时间节拍限频，保留原采集时间戳和点字段；导航仍直接使用全频 `/livox/lidar/geo_filtered`。

低速建图配置与现有低速定位一致，采用LiDAR线性去畸变，保留IMU互补滤波和倾角预处理；暂不采用已观测到同步扫描释放断档的后端IMU融合。此选择尚无高速或动态实机精度验收。减小ICP采样数量的实验没有消除断档，未保留1200/5000点配置。

实时会话状态分别报告原始位姿是否新鲜和是否仍在有效预测范围。旧位姿仍保留原时间戳；预测继续受里程计新鲜度、5秒、0.12米及0.20弧度上限约束，不能通过重复保留位姿刷新有效期。


## R2航向预测（2026-11-14移动数据修复）

导航本地里程计将平移速度和Z轴角速度分别按真实消息时间戳做梯形积分。航向不再逐帧直接采用底盘 `/odom.pose` 的yaw；该yaw在一次移动记录中有与定位及自身角速度不一致的跳动。初始yaw、真实时间断档后的yaw仍取原姿态；roll/pitch保留原值。这是R2平面移动预测，未修改底盘消息或底盘控制参数，不适用于据此宣称高动态三维姿态精度。

超过80ms的里程计时间断档仍建立新段并等待本段真实定位；角速度缺失、非有限或超预算拒绝。原有预测距离、转角、时间和纠偏跳变保护不放宽。纠偏跳变已锁定的旧进程不会被代码热更新自动清锁，停车后手动重启定位/建图链加载新实现；诊断优先显示锁定原因，不再误报成单纯位姿过期。


## 项目通信与建图采样节拍

项目GUI、甲方建图/定位和导航的脚本入口共用 `scripts/lib/ros_transport.sh`。`N01_RUNTIME_RMW=auto` 默认在私有运行依赖可用时选择CycloneDDS，缺失时明确警告并保留原通信实现；`N01_RUNTIME_RMW=rmw_fastrtps_cpp` 可显式回退。依赖目录默认 `n01_runtime/deps/cyclonedds/root/opt/ros/humble`，可用 `N01_CYCLONE_PREFIX` 指定。此设置仅作用于项目进程树，不会重启或修改桌面底盘、遥控、雷达/RSP入口；已有进程须停车后由GUI重新启动链路才加载。

采样器按采集时间固定节拍、容忍最多2ms抖动，补过已错失的时槽而不排队补发，保留原始点云及采集时间。之前逐次用“距上次转发至少200ms”判断，遇到199.xms就额外跳帧；新版测试10Hz加1ms抖动的输入仍转发约5Hz。突发丢帧后短期相邻输出可能相隔100ms，长期按5Hz节拍，不保证每对输出严格相隔200ms。每10秒日志报告接收/转发计数，可定位注册输入不足，而不是凭观察者单独收到的帧数推断发布频率。


## 感知通信与底盘控制通信分开配置

点云感知链可使用私有CycloneDDS以改善大消息接收。执行器、无地图短程工具、底盘模型参数读取及轨迹可行性监视仍采用FastDDS：当前Humble Cyclone环境的跨进程MessageInfo发布者标识与图端点标识不匹配，不能用既有GID比较来可靠排除自身命令。隔离私有话题实测100次自身零速消息，Cyclone监视器均报unknown；FastDDS仅报告READY，无误报。参见[ROS 2问题377](https://github.com/ros2/rmw_cyclonedds/issues/377)。不得以忽略未知来源或零速命令绕开手动优先。

控制入口在导入期间已加载错误RMW时，会在ROS初始化前以相同Python启动参数重新执行并选择FastDDS；若ROS上下文已运行则拒绝切换。启动脚本也在Python启动前显式选择控制RMW。该处理不改变运行中底盘的任何参数。

纯控制工具增加forward短程模式，上限0.1m、默认不执行、沿初始朝向移动并检查横向/航向漂移；命令积分预算同时包含两个平移分量。该工具仍用原始轮式里程计判断位置，不作为真实物理距离标定仪器。


## RViz物体轮廓显示

环境显示默认采用实测回波上的局部定向面片，而非占据体素立方体：以真实回波作面片中心，邻域PCA估计切平面，每个小面片独立，不跨越未观测空隙连接，不投影出方格地面外轮廓。参考地图和实时层仍分色；规划膨胀体保持单独调试开关。显示不会新增碰撞占据或改变规划地面过滤。

面片目标采样6cm、每层最多4000片，面片半径最大6.5cm；预算不足时稀疏采样，避免把物体扩成大方块。该显示保留已有回波形状，不做语义识别或凭空补全椅腿；已保存地图若本身20cm降采样，无法从它恢复细轮廓。重启导航显示节点及RViz加载新效果。

实时面片输入使用运动补偿实测 `/cloud`，不使用规划 `/grid_map/occupancy` 的栅格中心，避免轮廓在输入阶段已方块化。环境显示节点随导航启动/停止；仅打开导航RViz不会启动导航或显示节点，导航停止时该配置的曲面层没有发布者。可在仅建图时打开建图RViz查看地图。


## 类型化轨迹、连续性及模型

`scan_planner_msgs/Bspline.goal_id`来自原目标时间戳。GUI命令排队和实际发布保留同一ID；SCAN发布曲线时携带该ID，不依靠接收时间推断归属。`NavigationTrajectory`原子携带goal_id、revision、map_id、原始样条、预览、速度建议、URDF包络、实时参数、地面和场景。map_id由GUI提供PCD/模型哈希或本次SLAM会话标识；独立调用监视器时仅生成导航会话标识，不能拿它跨SLAM会话复用路线。

重复revision必须同几何/起点；旧goal、倒序revision、同ID冲突不得覆盖当前。原始样条起点与节点不改写。曲线首次接收必须有效；接受之后由控制器的实际进度钟驱动，而非按名义墙钟耗尽。每次续用仍需新鲜场景、真实模型和控制反馈。控制器向 `/n01/navigation/progress` 发布实际参数/弧长、执行用时及冻结状态，SCAN据此或实际位置估计进度，不再修改曲线start_time假装执行继续。

场景/模型有效与新轨迹准入分开。新提案被拒绝时，scene_valid只更新旧段的当前碰撞依据，不授权被拒曲线，也不提高旧段的已审核速度。有效旧段保留到需延伸或出现障碍；新证书先用于旧段的当前复核，等价左右提案不随刷新立即替换。替换检查当前位姿接续和移动中的朝向连续性；实际纠偏命令也按原生四轮模型及制动扫掠检查。普通局部更新复用全局参考，局部持续失败时才刷新A*，不每帧重建全局绕行侧。

环境名义余量为6cm，非定位精度承诺。生产碰撞模型必须有真实URDF投影，已删除三圆后备；当前包络覆盖轮组转向扫掠，属于保守的实体覆盖，不是每个瞬间最紧轮姿轮廓。离散运动检查另覆盖采样间隙。占用/原始全周点云按原时间对齐，过滤地面3cm及当前机身碰撞高度带；局部场景仅交付机器人附近4m范围，控制端不能越过证书覆盖范围假定无障碍。

场景采用紧凑PointCloud2字节数据，避免Python构造十万Point对象；相同XY占用做无几何损失去重。C++按空间格子索引，只查询当前扫掠附近障碍。高频控制不在GUI事件循环执行。实际有效范围和观测稀疏度仍取决于现场雷达，不承诺未知空间已探明。

运行模型及舵速/轮速上限由 `/chassis_controller/get_parameters` 读取，GUI不修改桌面控制器。配置入口为 `config/navigation.yaml`，GUI明确速度选择作为覆盖，内部后端/地图配置仍各归所属YAML；启动将所选配置哈希及显式覆盖写入 `n01_runtime/resolved/`。物理几何不在该入口复制一套默认值。

## 路线与启动

离线路线绑定PCD及坐标模型；实时路线可在本次SLAM会话保存/回放，SLAM重启后拒绝跨会话复用。每站来自真实停车状态，记录位置、朝向、关节、里程计和定位信息，运行先到原A，再依次到B等站点，确认停车和朝向后计时停留；不把当前位置重标为A。

暂停保留当前站点和剩余停留；继续从该站重新请求，不跳过失败站。GUI只处理任务、用户操作、地图绑定和反馈传输，不在移动循环里用网页缓存位姿另行暂停控制器。地图/坐标模型切换使旧控制任务失效，不能自动将旧路线重绑定。

GUI入口 `bash scripts/n01 gui`；导航感知/规划仍手动启动；行驶入口内部使用 `scripts/runtime/start_navigation_execution.sh`，只启动统一控制器且默认为disabled。单点和路线不会额外启动桌面底盘、雷达、遥控或RSP。当前主链不启用CBF，其开关明确禁用；保留纯算法研究代码供后续单独验收。

## 环境更新与障碍提取（2026-11-16接入，2026-11-17确认仍有缺口）

本节服务NAV-02、OBS-01/02、REC-01、SAFE-01及MOT-01。甲方提供传感器/定位/底盘，乙方维护导航环境、规划、跟踪与恢复；没有改动甲方共享预处理、建图定位算法或底盘驱动。下面记录已接入的模块；融合、覆盖和残留问题以本文件前部缺口说明及架构修订为准，不将算法回归等同于现场可用性。

### 点云入口与地面、自身过滤

`scene_perception.py`接入原`live_scan_bridge.py`，输入仍是经取证的当前扫描；读取现有`/robot_description`和`/joint_states`，按扫描时间插值关节，使用URDF box/cylinder/sphere及collision origin作几何包含过滤，不用笼统大框删除近处外物。轮自转编码器相位不改变实物轮外形，连续轮关节使用参考碰撞包络；腿和舵角必须有匹配时间的真实反馈。2026-11-16只读现场确认：RSP发布17个碰撞几何、ethercat发布12个腿/舵关节；未驱动车轮。

地面按1m分区从权威地面附近的低分位种子拟合，结合高度、坡度、残差及短期历史给出分类；不能把桌面/椅面仅因水平而升格为地面。过期/倒序帧不更新地面历史，证据不充分时保守保留。坐标不改写；`/cloud`增加FLOAT32 `ground`字段，仍保留真实地面XYZ端点用于射线清除，GridMap将该标签作为非占用端点。原有3cm地面过滤、5cm导航体素、6cm环境余量含义不变，均不表示可靠检出精度。原始没有回波或上游已删掉的物体不能由软件恢复。

### 环境状态与历史变化

GridMap保持log-odds命中/空闲概率，明确区分可信空闲、模糊/未知和占用，首次弱命中不能被当作空闲；逐体素记录原扫描时间；覆盖证据超过配置TTL回到未知；当前部分过期占用仍保留碰撞风险，需按架构修正为可解释的历史未确认层，不能声称已完成衰减。发布心跳不刷新原始观测时间。重复/倒序、超龄扫描不能刷新环境。清除只作用于真实射线穿过的高度，预测点不参加射线清除，不再整列删除椅面或护栏。

`static_free_evidence.h`在3次独立扫描、跨度0.3秒后确认空闲；1.5秒后不再称为新鲜空闲，但已否定的历史先验不直接恢复。`world_evidence.h`按世界三维体素保留确认变化，局部环形格子复用不会遗忘原区域，也不会将证据套到新区域；更新命中撤销旧清除。整图/坐标不连续重置和进程重启清除世界变化记录。新地图/SLAM会话仍必须重启导航，不能复用旧证据。

实时模式的碰撞查询只按实测障碍：当前真实机器人占位可作为启动的局部先验，运动轨迹与纠偏制动扫掠按实测障碍和机身投影检查；未观测不构成拒绝理由（2026-11-17五次修订）。`/grid_map/observed_free`表达局部二维覆盖；源码已尝试用实际射线投影替代机身高度密集切片，但现场适用性尚未验证，不声称完整三维体积均已扫描；已检测到的其他高度障碍继续由三维占用及碰撞包络处理。时间与来源保留，遮挡后方不凭空填成空闲。

### 动态风险、发布和共同查询

`dynamic_obstacles.py`使用当前实测障碍簇的时序关联及速度拟合，稳定运动证据满足后生成0.25/0.5/0.75秒预测位置及小位置不确定范围，不要求识别人或椅子类别。超时、重排、过大运动、拟合不一致和工作量超预算时不维持旧预测；实测障碍始终保留。预测是额外保守碰撞层，不保证不可预测的人运动。

显示层另提供 `/grid_map/reference_grid` 与 `/grid_map/live_grid`（`nav_msgs/OccupancyGrid`，5cm，-1/0/100），由同一三维体素缓冲区投影生成，仅供 GUI/RViz 显示，不是规划输入；规划仍使用三维体素与足迹包络。

`/n01/live_navigation/predicted_obstacles`由监视器发布，GridMap在独立预测层加入**全局A*软代价**与监视器降速建议，0.6秒超时独立失效；预测点不进入SCAN局部碰撞查询，不写入实测log-odds，不伪造LiDAR端点。执行证书包含实测/预测障碍；观测覆盖不再作为执行条件（2026-11-17五次修订，覆盖门控关闭后由实测障碍与数据时效承担）。审核和C++纠偏扫掠仍按整机身投影检查实测/预测障碍。

避让后的"恢复判定"（预测/实测清除、距离与相对速度、斜坡恢复、路径归位、滞回与事件证据）见[架构 §3.7](architecture.md#37-动态避让的恢复判定2026-11-17-设计待实施)；当前实现仍是速度自动恢复，尚无该判定。

占用与覆盖按相同发布版本成对提交，暂缺另一半时保持上一个有界有效的完整快照，避免混合新旧环境。占用发布改为遍历活跃观测地址，避免每次扫描完整三维窗口；历史硬占用在需要时独立合并。射线帧标记扩为32位，避免8位短周期回绕；计数使用32位以覆盖密集同体素回波。点云几何与地面计算放在原bridge的单个CPU工作线程中，ROS回调仅提交快照/收取结果；最多一帧在计算、一帧最新等待，不堆积FIFO。关节和模型按扫描时间快照，结果超龄、落后或模型更换则丢弃；原始消息不改写，发布仍在ROS executor中完成。GUI刷新不决定环境更新。关键环境/恢复参数集中在`config/navigation.yaml`，建图/定位输入和地面绑定仍由launch传入，不增加合同数值。

## 实时远目标、前沿推进与阻断恢复（2026-11-16）

全局A*可向当前累积地图之外的最终目标扩展乐观参考，离线模式同样通过`grid_map.extend_reference_to_goal`扩展，4百万格搜索资源上限不变。未观测区域按可通行处理，远端参考不等于已观测，原始目标和goal_id始终保留。

不设探索式改道：局部目标始终沿全局参考在窗口内选取并留出实际包络边缘，交由原生SCAN生成唯一局部曲线。`navigation/frontier.hpp`及前沿分支已于2026-11-17删除（盲区不推断）。原全局路线被实测确认阻断且局部无法接回时，走局部绕行或全局重规划，不另选探索前沿；两者均失败才等待/安全停止，不宣称到达。

### 目标受理与不可达判定（2026-11-17 按甲方口径）

目标受理以甲方地图为规划依据（IF-01），保证"有效起终点"（NAV-01）。已知占用目标拒绝有明文依据（[122]"路线避开地图中不可通行区域"）；**地图外目标接受且无额外推进限制**（2026-11-17五次修订：无明确障碍即可通行），需求书未规定该情形，需通过IF-04/OPEN-05与甲方补确认。受理失败码：`goal_known_occupied`/`goal_beyond_search_budget`。地图内未观测格按点云地图惯例视为可通行（无点即自由），但不生成空闲证据、不参与清除。

进入执行后，若目标或路径被实测阻断：先局部绕行，不可接续再全局重规划（REC-01）；两者都失败才进入等待或安全停止（SAFE-01），报`goal_unreachable_observed`，保留原始目标与goal_id，不自动改目标、不宣称到达，现场恢复或用户处置后可继续。窗口外未观测不构成失败或到达理由。

失败是否计入PERF-03成功率（OPEN-01）、受理≠可达的接口表述（OPEN-05）、500ms统计起止点（OPEN-02）仍待甲方确认。
